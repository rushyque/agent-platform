# 第一部分　基础概念

## 1.1 大语言模型（LLM）

**大语言模型**（Large Language Model，LLM）是一个**根据已有文本，预测下一个最小单位（token）**的概率模型。它不是数据库，不会"查询"事实，而是基于上下文进行续写。同一个问题，换个措辞、换个上下文，回答就可能不同。

几个必须理解的概念：

| 概念 | 含义 | 在控制台哪里能看到 |
|------|------|------|
| **token** | 模型处理文本的最小单位（英文约 ¾ 个单词，中文约半个到一个汉字） | Trace 的 `llm_response.usage`（用了多少 token） |
| **prompt** | 你**给**模型的全部输入文本（系统指令 + 历史对话 + 当前问题） | Trace 的 `llm_call.systemPrompt` / `messages` |
| **completion** | 模型**吐出**的回复文本 | Trace 的 `llm_response.rawText`、Playground 的"响应"区 |
| **上下文窗口（context window）** | 模型一次能"看见"的 token 上限，超出就要裁剪 | 看不见，但 Logs 里 `[compact]` 日志是它在裁剪 |
| **系统提示（system prompt）** | 最前面那段定义"你是谁、该怎么做"的指令 | Trace 的 `llm_call.systemPrompt`（全文） |

> **关键认知**：模型没有记忆。每次调用它，你都得把"相关历史"作为 prompt 重新喂给它。所谓"对话"，其实是每次都把历史消息拼进 prompt 再调一次。这就引出了后面的"上下文管理"。

## 1.2 流式响应（Streaming）

模型生成文本是**一个 token 一个 token**吐出来的。如果等整段生成完再一次性返回，用户要盯着空白屏等几秒甚至十几秒——这种延迟叫**首字延迟（TTFT, Time To First Token）**。

**流式响应**就是模型边吐、服务端边推、前端边显示。本系统用 **SSE（Server-Sent Events）** 协议做这件事：服务端持有一条长连接，每隔一小段就推送一条 `data: {...}\n\n` 的事件，前端收到就追加显示。

```
浏览器                         中台                         LLM(DeepSeek)
  │  POST /agent/x/run           │                              │
  │ ───────────────────────────► │  发起 chat 请求               │
  │                              │ ────────────────────────────► │
  │  ◄── data: TEXT_MESSAGE_CONTENT "你"   ◄── 吐出第 1 个 token │
  │  ◄── data: TEXT_MESSAGE_CONTENT "好"   ◄── 吐出第 2 个 token │
  │  ◄── data: TEXT_MESSAGE_CONTENT "，"   ◄── ...               │
  │  ◄── data: RUN_FINISHED              ◄── 生成结束             │
```

控制台里的**所有"实时"**都建立在这条 SSE 之上：Playground 的流式响应、Feed 的实时日志/轨迹/连接，本质都是 SSE 事件流。

## 1.3 工具调用（Function Calling）

纯聊天模型只会说话，不会**做事**（查数据库、调 API、算数）。**工具调用**让模型能"动手"：

1. 你事先告诉模型："你有这些工具，每个工具的名字、说明、参数如下。"
2. 模型在回复时，可以选择"我要调用某个工具"，并生成**结构化的调用参数**（不是自然语言）。
3. **你的代码**真正执行这个工具，拿到结果。
4. 把结果**回灌**给模型，模型基于结果继续生成。

这是一个**循环**：模型可能连续调用多个工具，直到它认为可以给用户最终答复。在本系统里，Hermes 模式的循环有**通用止损**：最多跑 30 步，且相同工具调用或相同助手文本重复出现时会提前中断，避免模型"原地打转"烧满步数。

```
用户："查一下最近的订单"
  ↓
模型 → 调用工具 query_orders({status:"pending"})
  ↓
代码执行 query_orders，返回 [{id:1,...}, ...]
  ↓
模型 看到结果 → 生成文本回复 "最近有 3 笔 pending 订单…"
```

在控制台的 **Trace** 面板里，你能清楚看到这个循环的每一步：`tool_call`（模型决定调工具）→ `tool_result`（代码执行完，回灌结果）→ `llm_response`（模型继续生成）。

## 1.4 请求与响应：一次调用的完整链路

这是**最核心**的一节。理解了一次请求的完整旅程，控制台里的一切就都通了。

### 请求方发起（HTTP POST）

前端（或任何客户端）要驱动 agent，就向中台发一个 HTTP 请求：

```
POST /agent/{agentId}/run
Authorization: Bearer <JWT>
Content-Type: application/json

{
  "threadId":  "playground-abc123",          // 哪个对话（线程）
  "runId":     "playground-abc123",          // 这次执行（run）的唯一 id
  "messageId": "playground-msg-abc123",
  "messages": [
    { "id": "playground-msg-abc123", "role": "user", "content": "你好" }
  ],
  "state": {},
  "tools": [],                               // 平台填，客户端留空
  "context": [],
  "forwardedProps": {}
}
```

- **`agentId`**（URL 路径里）：要找哪个项目 agent，比如 `freight_inquiry` 或 `starlink_factory`。中台不兜底，写错会明确报错。
- **JWT**（`Authorization` 头）：身份凭证。中台从中解出 `userId`、`role` 等，交给项目的 `resolveContext` 决定"这个用户能干什么"。
- **`messages`**：对话历史。第一条通常是这次的用户消息。

### 中台内部（factory）

中台收到请求，**对每一次 run 动态构建**一个 agent（"factory"模式）：

```
解析 JWT → 拿 userId
     ↓
调项目的 resolveContext → 拿业务上下文（role/scope/...）
     ↓
意图分类（classifyIntent）→ "order" / "sales" / "general"…
     ↓
按意图选工具子集（5 个聚焦工具 > 20 个）
     ↓
构建 system prompt（项目模板 + 上下文管理约定 + 上阶段摘要）
     ↓
路由：简单 → Hermes(BuiltInAgent)；复杂 → DAG(DAGAgent)
     ↓
streamText({ model, system, messages, tools })  ← 这里真正调 LLM
```

这一整串"思考过程"在普通聊天界面是**看不见**的。控制台的价值，就是把它**全部显形**：你能在 Logs 看到 `[Factory]` 决策日志，在 Trace 看到 `run.started` 里的 `intent` / `selectedTools` / `role` / `model`。

### 响应（SSE 事件流）

中台把这次 run 的全过程，作为一条 SSE 事件流推回去。典型的事件序列：

```
RUN_STARTED              ← run 开始，带回 input
TEXT_MESSAGE_START       ← 一段文本消息开始
TEXT_MESSAGE_CONTENT  Δ  ← 一个 token 片段（会重复很多次）
TEXT_MESSAGE_CONTENT  Δ
TEXT_MESSAGE_END
TOOL_CALL_START          ← 模型决定调工具
TOOL_CALL_ARGS           ← 工具入参
TOOL_CALL_END
TOOL_CALL_RESULT         ← 工具执行结果（回灌给模型）
TEXT_MESSAGE_START       ← 模型基于结果继续生成
TEXT_MESSAGE_CONTENT  Δ
TEXT_MESSAGE_END
RUN_FINISHED             ← run 结束
```

> 每个 `Δ` 都是一条独立的 SSE 事件，前端累加起来就是你看到的流式文本。

**如果出错**：会收到 `RUN_ERROR`（带 message）替代 `RUN_FINISHED`。

## 1.5 会话与线程

- **thread（线程）**：一段**对话**。同一个 thread 里，历史消息会被带到每次请求。`threadId` 标识它。
- **run（一次执行）**：线程内的**一次**模型调用循环。一个线程可以有多次 run（用户问一句 = 一次 run）。`runId` 标识它。

> 在本控制台的**实时观察层**里，事件是按 **run** 聚合展示的（Trace 面板按 `runId` 归组）。thread 的概念主要用于中台自身的持久化（恢复历史对话），控制台本期不做历史回放。

# 第二部分　中台的设计

## 2.1 为什么需要"中台"

设想你有三个系统：销售管理、HR、货运询价，每个都想接 AI agent。如果每个系统各自实现一套"调 LLM、管工具、存对话、做认证"，会重复造轮子，且每个系统的 agent 质量参差不齐。

**中台**的思路：把"怎么传"抽出来做成共享基础设施——认证、持久化、可观测、模型调用、工具注册、上下文管理——而把"传什么"留给具体业务项目。

项目接入只需实现一个 **`AgentConfig` 契约：

```
AgentConfig = {
  agentId, tools,                    // 我提供哪些工具
  resolveContext,                    // 从 JWT 解出我的业务上下文
  buildSystemPrompt,                 // 模型该听什么指令
  classifyIntent / selectTools?,     // （可选）意图分流
  dagDefinition?,                    // （可选）复杂场景的 DAG
}
```

平台不解读 `role` / `scope` / `department` 这些字段——销售系统返回 `{role, scope}`、HR 返回 `{department, clearance}`，平台一视同仁，只负责把它们透传到工具和 prompt。

## 2.2 两种执行模式：Hermes 与 DAG

| 模式 | 谁在决策 | 适用 | 在控制台标识 |
|------|---------|------|------|
| **Hermes** | LLM 自主（function calling 多步循环） | 查询、问答、轻量多步 | Trace `route: hermes`，Runs 面板蓝色标签 |
| **DAG**（Harness） | 代码确定性编排（预定义步骤图） | 月报生成、多步审批、强流程 | Trace `route: dag`，Runs 面板琥珀色标签 |

**原则（简单性层级）**：从 Hermes 开始。只有当**有测量证据**表明模型频繁犯错、或任务有强确定流程时，才升级为 DAG。不要一上来就 DAG。

在控制台 Trace 里你能直观看到两者的区别：
- Hermes：一串 `llm_call → llm_response → tool_call → tool_result → llm_response …`，模型自主决定下一步。
- DAG：规整的 `run.step` 序列（每步 `type: tool / llm / condition / transform`），由代码编排。

## 2.3 上下文管理：折叠、摘要、artifact 外置

模型上下文窗口有限，长对话会让 prompt 膨胀，进而触发**幻觉**（DeepSeek 尤其敏感）。中台有三层应对：

1. **工具结果外置**：工具返回的大块数据，**不**直接塞进 prompt，而是落到 artifact 表；prompt 里只放一个**短摘要 + 引用** `{ref, toolName, summary}`。模型需要完整细节时，**主动调用** `getArtifact(ref)` 取回。
2. **折叠**：较老的工具结果被替换成更短的折叠占位（带 `ref=art-xxx`）。
3. **线程摘要**：每轮 run 结束，把"上阶段摘要 + 本次对话"压成一段，下轮注入 system。

在 Trace 里你会看到工具结果只有 `summary` 和 `ref`；在 Logs 里会看到 `[compact]` / `[summarize]` 日志记录这些裁剪动作。

## 2.4 权限双层面

- **软约束（模型权限意识）**：把"你是谁、能做什么、不能做什么"写进 system prompt，让模型**尽量**不产生越权调用。
- **硬约束（工具权限校验）**：每个工具的 `execute` 内部**自己**校验权限。即使模型判断失误真的调了，也会被工具拦下，返回**结构化错误**（`{ok:false, message, suggestion}`），而不是抛异常。模型看到结构化错误，能理解原因并给用户有意义的回复。

控制台的 **Playground** 正是验证这两层的好地方——你可以伪造任意 `role` 触发权限拒绝，观察模型如何回应。

## 2.5 观察层的设计哲学

控制台的观察层有意识地做了两个取舍：

1. **只做实时，不做存储**（零 DB）。所有日志、LLM 输入输出、连接信息，都走进程内**环形缓冲**（最近 30 分钟）+ 一条**多路复用 SSE**。代价是：重启即清零、没有长窗口历史。
   - **为什么**：观察台的使命是"现场看清楚"，不是"事后做报表"。要看一个过去的 run，用 Playground 同条件重跑一遍即可——**以可复现换不落库**。
2. **一条 SSE，多路复用**。所有通道（`logs` / `runs` / `connections`）复用一条 `/observe/stream`，事件带 `channel` 标签区分，前端按标签分流。一条连接、一套订阅，和 AG-UI 自己的 SSE 模型一致。

# 第三部分　控制台使用详解

## 3.1 进入控制台

**首次或更新前端后**，需要构建一次 SPA（控制台是独立的 Vite 工程）：

```bash
npm --prefix console install      # 装依赖（首次）
npm --prefix console run build    # 构建 → console/dist
```

或者直接用一键脚本（自动补依赖 + 构建 + 起服务）：

```bash
npm run go          # 开发模式（tsx watch）
npm run go:prod     # 生产模式（tsc + node dist/server.js）
```

服务起来后，浏览器打开：

```
http://<RUNTIME_HOST>:<RUNTIME_PORT>/console
```

> 如果页面显示 `{"error":"console not built"}`，说明没构建前端——回到上一步执行 `npm --prefix console run build`。

## 3.2 顶部导航与连接状态

页面最顶部是一条导航栏，从左到右：

| 元素 | 含义 |
|------|------|
| **品牌名** | "Agent Platform · 观察控制台" |
| **实时 Feed** / **Agents** / **Playground** | 三个视图的切换入口（当前页高亮） |
| **右上一个圆点 + 文字** | **SSE 连接状态**。🟢 绿色"已连接"= `/observe/stream` 已连上，能收到实时事件；🔴 红色"连接中…"= 断开/重连中（EventSource 会自动重连，不用管） |

> 如果一直是红色：检查中台是否在跑、`OBSERVE_ENABLED` 是否为 `false`、`OBSERVE_TOKEN` 是否匹配（见 [5. 故障排查](#第五部分故障排查与已知限制)）。

## 3.3 实时 Feed 视图

控制台默认视图，**四栏**从左到右：

```
┌──────────────┬─────────┬────────────────┬─────────┐
│    Logs      │  Runs   │     Trace      │  连接   │
│ (全仓日志)   │ (run列表)│ (选中run的轨迹) │ (HTTP) │
└──────────────┴─────────┴────────────────┴─────────┘
```

### 3.3.1 Logs 面板（最左，最宽）

展示中台**全仓的结构化日志**。每一行一条日志：

```
10:26:21.496  [replay] [info] Startup  runtime listening  {"url":"http://..."}
  ↑时间戳      ↑回放标记 ↑级别 ↑来源    ↑消息           ↑结构化数据
```

- **过滤框**：实时按 `source` / `msg` / `runId` / `data` 子串过滤（大小写不敏感）。
- **级别下拉**：只看某个 level（`debug / info / warn / error`）。`error` 行有红底、`warn` 有琥珀底，便于扫视。
- **`replay` 标签**：这条日志是**你连上控制台时**从环形缓冲回放的历史（30 分钟内）；没有这个标签的就是连上之后的实时日志。
- **`runId` 标签**（蓝色，8 位）：这条日志归属哪个 run。工具执行、factory 决策等的日志会带它，方便你把日志和 Trace 对上号。
- **右侧 data**：结构化字段（JSON）。比如工具日志会带 `{tool, execMs, resultChars, ...}`。

**右侧的计数**是当前过滤后的日志条数。

> 常见 `source`（标签）：`Startup`（启动）、`Factory`（每次 run 的路由决策）、`tool`（工具执行）、`artifact`（工具结果外置）、`compact` / `summarize`（上下文压缩）、`thread-memory`（线程摘要）、`DB`（数据库）、`DAG`（DAG 步骤）、`Audit`（审计/计费）、`stall`（流式卡顿检测）。

### 3.3.2 Runs 面板（左中）

按时间倒序列出最近的 run（来自 `run.started` 事件）。每个卡片：

```
[hermes] [freight_inquiry] [order] [ok]      ← 标签行
playground-abcd123 · 10:30:15 · 1320ms        ← runId / 开始时间 / 耗时
```

- **`[hermes]` / `[dag]`**：路由模式，蓝色=Hermes，琥珀=DAG。
- **agent 标签**：哪个 agent 跑的。
- **intent 标签**（如有）：意图分类结果。
- **状态标签**：`ok`（绿）= 正常结束，`error`（红）= 出错，没有状态标签 = 还在跑。
- **点击某个 run** → 右侧 Trace 面板显示它的完整轨迹。

### 3.3.3 Trace 面板（中右）

**控制台最有价值的面板**。显示选中 run 的**逐步轨迹**，把一次 run 从生到死拆成一系列事件：

| 事件类型 | 你能看到什么 |
|---------|------|
| **`started`** | 这次 run 的"身份证"：`agentId` / `route`(hermes/dag) / `intent` / `role` / `model` / `selectedTools`（实际暴露给模型的工具子集）。**这能回答"模型到底看到了哪些工具"**。 |
| **`llm_call`** | 一次 LLM 调用的**输入**：`systemPrompt` 全文长度、`messages` 条数、`stepIndex`。回答"prompt 是什么样"。 |
| **`tool_call`** | 模型决定调工具：`toolName` + 完整 `args`。 |
| **`tool_result`** | 工具执行完：`execMs`（耗时）/ `summary`（短摘要）/ `ref`（artifact 引用，点不进去，但知道完整数据被外置了）。 |
| **`llm_response`** | LLM 的**输出**：`rawText`（这段回复的完整文本）/ `usage`（token 用量，可能为 null）/ `finishReason` / `stepIndex`。 |
| **`step`**（仅 DAG） | DAG 的一步：`stepIndex` / `type`(tool/llm/condition/transform) / `stepId`。 |
| **`finished`** | run 结束：`status`(ok/error) / `durationMs` / `message`（出错时的原因）。 |

> Hermes 的多步循环会看到 `llm_call` → `llm_response` → `tool_call` → `tool_result` → `llm_response` … 的交错序列。每一步都能点开看详情。

### 3.3.4 连接面板（最右）

记录**谁在打中台**——所有 `/agent/*` 与项目路由（`/game` / `/inquiry`）的 HTTP 请求（静态资源不计）。

```
[POST] /agent/freight_inquiry/run  [console] [200]
10:30:15 · 1320ms · agent=freight_inquiry · user=tester · 127.0.0.1
```

- **method 标签**：`POST` 蓝色（驱动 run 的请求），其它灰色。
- **path**：请求路径。
- **`[console]` 标签**（绿）：这个请求来自控制台自己（Playground 发出的请求会带 `X-Observe-Origin: console` 头）。
- **状态码**：`2xx` 灰、`4xx/5xx` 红、`…`（琥珀）= 还没返回。
- 下面一行：开始时间、耗时、agentId、userId、来源 IP。

`request.started` 和 `request.finished` 用同一个 `reqId` 关联。

## 3.4 Agents 视图

展示中台**当前注册的 agent 清单**（来自 `/console/api/agents`，内存中的 AgentConfig 注册表）。每个 agent 一张卡：

- **`[id]`**（蓝）：agentId，比如 `starlink_factory`。
- **`[Hermes]` / `[DAG (Harness)]`**：绿=Hermes，琥珀=DAG。
- 描述文字：这个 agent 是干什么的。

> 这里只读。要驱动某个 agent，去 Playground。

## 3.5 Playground 视图（核心）

**Playground 是控制台的灵魂**——它让你**扮演请求方**，亲手触发一个 run，并实时观察它的内部。

界面分三块（从上到下）：**身份** / **对话** / **原始事件**。

### 第一步：签发身份（"我是谁"）

```
[选 agent ▼] [userId] [role] [签发 token]  [未签发 / 已签发(tester/admin)]
[额外 claims JSON 文本框]
```

1. **选 agent**：下拉选一个（如 `starlink_factory`）。
2. **填 `userId` 和 `role`**：随便填。`role` 是测权限的关键——填 `admin` / `manager` / `salesperson`，看项目工具是否按角色放行。
3. （可选）**claims JSON**：往 JWT 里塞额外字段，比如 `{"department":"华东"}`。
4. 点 **「签发 token」**。

中台会用 `JWT_SECRET` **现场签发**一个 JWT，存到浏览器 localStorage（`observe_agent_jwt`）。状态标签变绿 "已签发 (tester/admin)"。

> 这个 token 只在你浏览器里，每次重签覆盖旧的。关掉浏览器标签不会丢（localStorage 持久），但要清楚：这是**测试用**的伪造身份，不是真实 SSO。

### 第二步：发消息

```
[消息文本框]                 [发送 / 中断]
[响应（流式）区域]
```

1. 在文本框输入消息，比如"查一下最近的订单"。
2. 点 **「发送」**（或 `Ctrl+Enter`）。

前端会：
- 构造 [1.4 节](#14-请求与响应一次调用的完整链路)描述的请求体（自动生成 `threadId` / `runId`）；
- `POST /agent/{agentId}/run`，带 `Authorization: Bearer <你刚签发的 token>` 和 `X-Observe-Origin: console`；
- **流式**接收响应，逐字追加到"响应"区域。

发送中按钮变成 **「中断」**（调用 `AbortController.abort()` 取消请求）。

### 第三步：同时看内部轨迹

**重点**：发出去的同时，切到（或并排打开）**实时 Feed** 视图——你会看到：

- **连接面板**多了一条 `[console]` 标记的 `POST /agent/.../run`，状态从 `…` 变 `200`。
- **Runs 面板**冒出一条新 run 卡片。
- **点开它** → **Trace 面板**实时展开：`started` → `llm_call`（你那句话 + system prompt 全文）→ `tool_call` / `tool_result`（模型调了什么工具、拿到什么）→ `llm_response`（生成的文本，和 Playground 响应区一致）→ `finished`。
- **Logs 面板**同步滚动出 `[Factory]` 决策、`[tool]` 执行、`[compact]` 压缩等日志。

**Playground 响应区**给最终用户视角（看到的话），**Feed 的 Trace** 给开发者视角（为什么这么答）。两边对照，是理解 agent 行为最快的路径。

### 第三块：原始 AG-UI 事件

最下面那块，按到达顺序列出这次 run 收到的**原始 AG-UI 事件**（`RUN_STARTED` / `TEXT_MESSAGE_CONTENT` / `TOOL_CALL_*` …）。调试协议层问题时用——比如"模型到底发了几个 text-delta"、"工具结果事件长什么样"。

## 3.6 事件类型速查表

控制台所有事件都是 envelope：`{channel, type, ts, payload, replay?}`。

### `logs` 通道
| 字段 | 含义 |
|------|------|
| `level` | debug / info / warn / error |
| `source` | 日志来源（Startup / tool / Factory / …） |
| `msg` | 消息 |
| `data` | 结构化字段（可选） |
| `runId` / `threadId` / `agentId` | 归属（可能为 null，如启动日志） |

### `runs` 通道
| `type` | payload 关键字段 |
|--------|------|
| `run.started` | `agentId`, `route`, `intent`, `selectedTools`, `role`, `model` |
| `run.llm_call` | `systemPrompt`, `messages`, `stepIndex` |
| `run.llm_response` | `rawText`, `usage`(可空), `finishReason`, `stepIndex` |
| `run.tool_call` | `toolName`, `args` |
| `run.tool_result` | `toolName`, `execMs`, `summary`, `ref` |
| `run.step`（DAG） | `stepIndex`, `type`, `stepId` |
| `run.finished` | `status`(ok/error), `durationMs`, `message?` |

### `connections` 通道
| `type` | payload 关键字段 |
|--------|------|
| `request.started` | `reqId`, `method`, `path`, `agentId?`, `userId?`, `ip`, `origin`, `ua` |
| `request.finished` | `reqId`, `status`, `durationMs` |

# 第四部分　常见任务操作指南

**「我想看一次 run 用了哪些工具」**
→ Playground 发消息 → Feed 的 Runs 点开那条 run → Trace 里看 `tool_call` / `tool_result` 序列；或看 `started` 的 `selectedTools`（模型实际"看到"的工具子集）。

**「我想验证权限是否生效」**
→ Playground 用 `role: salesperson` 签发 → 发一句越权请求（如"审核这笔汇款"）→ 在 Trace 的 `tool_result` 里看是否返回 `{ok:false, message:"无权…"}` 结构化拒绝；同时看 Playground 响应区模型如何转述。

**「我想排查 run 报错」**
→ Runs 面板找 `[error]` 红标的 run → Trace 末尾的 `finished` 看 `message` → Logs 面板按那个 `runId`（点日志上的蓝标签或粘到过滤框）过滤，看 `[tool] threw` / `[DB]` 等错误日志。

**「我想看模型实际收到的 system prompt」**
→ Trace 的 `llm_call` 事件 → payload 里的 `systemPrompt` 全文长度；完整 prompt 文本在 payload 里（前端 Trace 卡片显示长度，需要全文可展开原始 payload）。

**「我想对比两次 run」**
→ 连发两次同样的话 → Runs 面板会有两条 → 分别点开看 Trace 差异（选的工具不同？耗时不同？token 不同？）。

**「Playground 响应区空着，没反应」**
→ 先看身份是不是"已签发"（没签会红字提示"先点签发 token"）→ 再看下方"原始 AG-UI 事件"有没有动静 → 看 Feed 的连接面板这条请求状态码 → 看 Logs 有无 `[Runtime]` 错误。

# 第五部分　故障排查与已知限制

| 现象 | 原因 / 处理 |
|------|------|
| 打开 `/console` 返回 `{"error":"console not built"}` | 前端没构建。执行 `npm --prefix console install && npm --prefix console run build`，或 `npm run go`。 |
| 顶部连接指示灯一直红色 | 中台没起 / `OBSERVE_ENABLED=false` / 配了 `OBSERVE_TOKEN` 但浏览器没存对。把 admin token 存进 localStorage 的 `observe_admin_token`，或在 dev 关掉 token。 |
| Runs 面板空空如也 | 没有跑过 run。去 Playground 发条消息触发一次。 |
| Trace 里看不到 `tool_call` | 这次 run 没调工具（纯文本问答）。正常。 |
| `llm_response.usage` 是 null | DeepSeek 偶发不返回 usage 字段。已知，不影响功能。 |
| 重启中台后，之前的 run/日志全没了 | 观察层零 DB，环形缓冲重启即清零。要看旧 run，用 Playground 重跑。**这是设计取舍，不是 bug。** |
| 浏览器里 `/console` 子路径刷新 404 | 中台对 `/console/*` 做了 SPA fallback；如果走的是反代（如 nginx），需在反代层也配置 fallback 到 `index.html`。 |
| Playground 报 `HTTP 401` | JWT 过期或没签发。重新点"签发 token"。 |
| Playground 报 `HTTP 500` | 中台内部错。看 Logs 的 `[Runtime]` / `[UncaughtException]`，或 Trace 的 `finished.status:error`。 |

**已知限制（本期）**：
- **无历史回放**：观察层不落库，没有"昨天的 run"。靠 Playground 可复现。
- **Hermes 多步循环**：只捕获第一次 `llm_call` 的完整 prompt（systemPrompt + 初始 messages）；中间步骤的 prompt 由 AI SDK 内部组装，无法直接抓取——但每一步的 `llm_response` 都有。
- **DAG 的 `usage` 可选**：DeepSeek 不总是返回 token 用量。

# 附录　术语表

| 术语 | 含义 |
|------|------|
| **LLM** | 大语言模型，基于上下文预测下一个 token 的模型 |
| **token** | 模型处理文本的最小单位 |
| **prompt** | 给模型的输入（system + 历史 + 当前问题） |
| **completion** | 模型的输出 |
| **streaming / SSE** | 边生成边推送的协议（Server-Sent Events） |
| **TTFT** | 首字延迟，从发请求到第一个 token 到达的时间 |
| **function calling / 工具调用** | 模型生成结构化调用，代码执行后回灌结果的多步循环 |
| **agent** | 能调工具、多步决策的 LLM 应用 |
| **AG-UI** | CopilotKit 的 agent-UI 协议（SSE 事件流：RUN_STARTED / TEXT_MESSAGE_CONTENT / TOOL_CALL_* / RUN_FINISHED …） |
| **thread** | 一段对话（多条消息的容器） |
| **run** | 线程内的一次模型执行循环 |
| **Hermes** | LLM 自主决策的执行模式（function calling） |
| **DAG / Harness** | 代码确定性编排的执行模式 |
| **artifact 外置** | 工具大结果落库、prompt 里只放 {ref,summary} 的上下文管理手段 |
| **AgentConfig** | 项目接入中台的契约（agentId / tools / resolveContext / buildSystemPrompt / ...） |
| **环形缓冲** | 固定容量、满了丢最早的内存缓冲（观察层用它保留"最近 30 分钟"） |
| **replay** | 客户端连上 SSE 时，服务端先把环形缓冲里的历史事件标 `replay:true` 推一遍 |
| **factory** | 中台对每次 run 动态构建 agent 的模式（按请求解析上下文 → 选工具 → 组 prompt → 路由） |
| **ALS** | AsyncLocalStorage，Node 里给异步调用链打"上下文标签"的机制（这里用于日志按 run 归属） |
