# Agent 中台 · 业务系统对接规范

> 给业务系统加一个 AI 对话助手时，照这份文档对接中台。
> 假设你有一个正常的业务系统（有自己的后端 API + 前端），现在想给它加一个"对话助手"。
> 你拿到的代码包是中台的**核心后端**（`src/` 下除 `projects/` 之外的部分是平台核心，`projects/` 是两个示例项目）。

---

## 0. 一句话定位

**中台是一个"Agent 运行时"**：你告诉它"我有这些业务工具、模型该扮演谁"，它负责把 LLM、工具调用、流式输出、对话持久化、上下文压缩、鉴权全部跑通，对外暴露一个标准的 AG-UI HTTP 端点。你的前端只要会发 HTTP 请求、读 SSE 流，就能有一个完整的对话助手。

**核心设计哲学：平台只管"怎么传"，不管"传什么"。**
平台不认识"订单""客户""汇款"这些业务概念，它只负责把你的工具接到 LLM、把 LLM 的输出流给前端。所有业务语义（角色、权限、领域知识）都由你写在工具和 prompt 里。

## 1. 全景架构

```
┌──────────────────────────────┐
│  你的前端（Vue 3）             │   ← 第 7 节：怎么发请求、读 SSE
│  聊天 UI + 工具结果渲染         │
└─────────────┬────────────────┘
              │ HTTP POST + SSE（AG-UI 协议）
              │ POST /agent/{agentId}/run
              ▼
┌──────────────────────────────────────────┐
│  中台 Runtime（你拿到的核心后端）            │
│  ├─ JWT 鉴权 → 解析 userId                  │
│  ├─ 按 agentId 找到你的 AgentConfig          │
│  ├─ 调你的 resolveContext → 业务上下文        │
│  ├─ 调你的 buildSystemPrompt → system prompt │
│  ├─ 把你的 tools 包装成 AI SDK 工具           │
│  ├─ streamText 多步循环（含上下文压缩）        │
│  ├─ 工具结果外置（artifact）+ getArtifact     │
│  └─ 事件持久化 + 审计 + SSE 输出              │
└─────────────┬────────────────────────────┘
              │ 你的工具 execute 里调
              ▼
┌──────────────────────────────┐
│  你的业务后端（NestJS / 任何）   │   ← 第 4 节：工具里 fetch 你的 API
│  /api/orders /api/customers …  │
└──────────────────────────────┘
```

## 2. 接入全景（5 步）

1. **在 `src/projects/你的项目/` 下建目录**，写一个 `agent-config.ts`（实现 `AgentConfig`）。
2. **写工具**（`tools/*.ts`），每个工具用 Zod 定义参数，`execute` 里调你的业务后端 API。
3. **写 prompt**（`prompts.ts`），告诉模型它的角色、能用什么工具、业务约束。
4. **在 `src/projects/index.ts` 注册两行**：`registerAgent(...)` + 可选 `registerProjectRoutes(...)`。
5. **前端**：Vue 组件里 POST 到 `/agent/{agentId}/run`，读 SSE 流。

启动 `npm run dev`（默认 9876 端口），你的助手就上线了。

## 3. 后端：实现 AgentConfig（核心契约）

`AgentConfig` 是你和中台唯一的契约（[src/types/agent-config.ts](../src/types/agent-config.ts)）。完整字段：

```ts
import type { AgentConfig } from "../../types/agent-config.js";

export const myAgentConfig: AgentConfig = {
  agentId: "my_business",            // ① 全局唯一，URL 路径里用：/agent/my_business/run
  description: "xx 系统对话助手",      // ② 给调试台看

  // ③ 从 JWT 解析出的 {userId, token, headers} → 你返回任意业务上下文
  resolveContext: async ({ userId, token, headers }) => ({
    userId,
    role: "sales",                   // 你自己定的业务字段，平台不解读
    name: "销售助手",
    apiBase: "http://localhost:3001",// 你的业务后端地址
    token,                           // 可透传给工具，调你后端时带鉴权
  }),

  // ④ 你的工具集
  tools: [/* ... */],

  // ⑤ 构建 system prompt（平台每轮调一次，透传 intent 避免重复分类）
  buildSystemPrompt: ({ context, messages, intent }) =>
    `你是${context.name}，${context.role}角色。……`,

  // ⑥ 可选：意图分类（缺省 "general"）。要聚焦工具子集时才需要
  classifyIntent: ({ messages, context }) => {
    const text = [...messages].reverse().find(m => m.role === "user")?.content ?? "";
    if (/订单|出货|交期/.test(text as string)) return "order";
    if (/客户|联系人/.test(text as string)) return "customer";
    return "general";
  },

  // ⑦ 可选：按意图选工具子集（缺省暴露全部工具）
  selectTools: ({ intent, allTools }) =>
    intent === "order" ? allTools.filter(t => t.name.includes("order")) : allTools,

  // ⑧ 可选：指定模型（缺省用平台的 DeepSeek）
  model: "deepseek-chat",

  // ⑨ 可选：复杂多步编排走 DAG（见第 4.6 节，存在则该 agent 不走默认 Hermes 模式）
  // dagDefinition: { steps: [...] },
};
```

> **关键**：`resolveContext` 返回的对象会原样透传给每个工具的 `execute(args, context)`，也会注入到 `buildSystemPrompt`。平台不关心里面有什么字段——SalesHub 放 `{role, scope}`，HR 系统放 `{department, clearance}`，都行。

## 4. 后端：工具设计规范（重点）

工具是 LLM 调你业务系统的桥。一个工具 = 一个函数声明（Zod 参数）+ 一个执行函数（调你的 API）。

### 4.1 ToolDefinition 结构

```ts
import { z } from "zod";
import type { ToolDefinition } from "../../types/agent-config.js";

export const queryOrdersTool: ToolDefinition = {
  name: "mybiz_list_orders",          // ① 命名见 4.2
  description: "查询订单列表，支持按客户、状态过滤。返回订单号、客户、金额、状态、交期。", // ② 给模型看，写清楚"能查什么、返回什么、何时用"
  parameters: z.object({               // ③ Zod schema，自动转成模型工具签名
    customer: z.string().optional().describe("客户名，模糊匹配"),
    status: z.enum(["pending", "shipped", "done"]).optional().describe("订单状态"),
    limit: z.number().optional().describe("最多返回条数，默认 20"),
  }),
  execute: async (args, context) => {  // ④ context 就是 resolveContext 的返回值
    const resp = await fetch(`${context.apiBase}/api/orders?` + new URLSearchParams({
      ...(args.customer ? { customer: args.customer } : {}),
      ...(args.status ? { status: args.status } : {}),
      limit: String(args.limit ?? 20),
    }), {
      headers: { Authorization: `Bearer ${context.token}` },
    });
    if (!resp.ok) throw new Error(`业务后端 ${resp.status}`);
    const data = await resp.json();
    return { count: data.length, orders: data }; // ⑤ 返回任意 JSON，见 4.4
  },
};
```

### 4.2 命名规范（重要，有坑）

**格式：`{projectId}_{动词}_{对象}`**，如 `mybiz_list_orders`、`mybiz_get_order_detail`、`mybiz_approve_refund`。加项目前缀避免多项目工具名冲突。

> **⚠ 只读查询工具，名字里要含 `view` / `list` / `detail` 之一。**
> 中台有上下文压缩（治 DeepSeek 多步幻觉，见第 10 节），策略默认按工具名匹配：名字含 `view`/`list`/`detail` 的工具结果**不折叠**（模型一次看清，不重查）；写操作工具的结果会折叠。**如果你的只读工具起名 `mybiz_query_orders`（不含那三个词），它的结果会被折叠，DeepSeek 会反复重查、编造数字、死循环**——这是真实踩过的坑。所以查询类工具请用 `list_` / `view_` / `_detail` 命名。

### 4.3 参数：用 Zod

- 用 `z.object({...})`，字段 `.describe("...")` 描述会传给模型，**描述质量直接决定模型会不会正确传参**。
- 枚举用 `z.enum([...])`，可选用 `.optional()`。
- 复杂结构用嵌套 `z.object` / `z.array`，但**能简单就简单**——参数越复杂模型越容易传错。

### 4.4 返回值约定

`execute` return 任意 JSON，平台会自动处理两件事：

1. **外置**：结果存入 artifact，context 里只给模型看 `{ref, toolName, summary}`（短摘要），需要完整数据时模型自己调平台注入的 `getArtifact(ref)`。**你不用管，直接返回完整结果即可。**
2. **错误信封**：
   - **`execute` 正常 return** → 按业务结果原样返回。建议结构：
     - 成功：`{ ok: true, ..., 数据 }` 或直接 `{ count, orders }`
     - 业务拒绝（如状态不允许）：`{ ok: false, message: "订单已是已发货状态，无法取消", ... }`（前端显示琥珀色"拒绝"）
   - **`execute` 抛异常** → 平台自动包成 `{ ok: false, error: true, message: "工具执行异常: xxx" }`（前端显示红色"错误"）。所以**网络错误、后端 5xx 直接 throw 即可**，不用自己 try/catch。

### 4.5 权限校验（双层）

模型权限意识（prompt 里写）+ 工具硬校验（execute 里写）：

```ts
export const approveRefundTool: ToolDefinition = {
  name: "mybiz_approve_refund",
  description: "审批退款申请。仅财务经理/admin 可用。",
  parameters: z.object({ refundId: z.string() }),
  execute: async (args, context) => {
    // 硬约束：即使模型判断失误调到这里，也拦住
    if (!["finance_manager", "admin"].includes(context.role)) {
      return {
        ok: false,
        message: "当前角色无权审批退款",
        suggestion: "请联系财务经理处理",
      };
    }
    // ... 调后端审批
  },
};
```

权限拒绝**不要抛异常**，return 结构化结果，让模型能给用户有意义的回复。

### 4.6 进阶一：工具内部调 LLM 做结构化提取

如果某个工具本身需要 AI（比如"解析报价邮件→结构化数据""评估推荐"），可以在 `execute` 里用平台的 `createLLMClient()` + `generateObject`：

```ts
import { generateObject } from "ai";
import { z } from "zod";
import { createLLMClient } from "../../../core/llm.js";

export const parseEmailTool: ToolDefinition = {
  name: "mybiz_parse_quote_email",
  description: "用 AI 解析报价邮件正文，提取运费/单价/时效等结构化字段。",
  parameters: z.object({ emailId: z.string() }),
  execute: async (args, context) => {
    const email = await getEmail(args.emailId); // 调你后端
    const { object } = await generateObject({
      model: createLLMClient(),                 // 复用平台的 DeepSeek
      schema: z.object({
        freight: z.number(),
        unitPrice: z.number(),
        transitDays: z.number(),
        airline: z.string(),
      }),
      prompt: `从以下邮件提取报价字段：\n${email.body}`,
    });
    return { ok: true, parsed: object };
  },
};
```

> 这样模型（主对话）只看到工具返回的精简结构化结果，不用自己去解析长邮件正文——上下文干净、准确率高。完整范例见 `src/projects/freight-inquiry/tools/ai.ts`。

### 4.7 进阶二：DAG 编排（复杂多步）

如果你的任务是**确定性多步流程**（如"收集数据→分析→生成月报"），可在 AgentConfig 里加 `dagDefinition`，平台会走 DAGAgent 而非默认的 LLM 自主循环。DAG 步骤类型有 `llm` / `tool` / `condition` / `transform`。**绝大多数对话助手用不到，从默认 Hermes 模式开始**。需要时参考 [src/types/agent-config.ts](../src/types/agent-config.ts) 的 `DAGDefinition`/`DAGStep` 和 `src/core/dag/`。

## 5. 鉴权：JWT

中台**信任传入的 JWT**，自己不做登录。流程：

```
你的登录系统签发 JWT（payload 含 userId）
   → 前端把 JWT 存 localStorage
   → 每次请求带 Authorization: Bearer <jwt>
   → 中台用 JWT_SECRET 验签，取 payload.userId
   → 调你的 resolveContext({ userId, token, headers })
```

**JWT payload 字段**：中台按 `id` → `userId` → `sub` 的顺序取 userId（[src/core/middleware/auth.ts](../src/core/middleware/auth.ts)）。其余字段（role 等）你可以自己塞 payload，但**推荐在 `resolveContext` 里根据 userId 查你自己的库拿角色**，而不是信任 JWT 里的 role（前端可篡改 JWT 之外的字段时更安全）。

**`JWT_SECRET` 必须和中台 `.env` 里的一致**，否则验签失败、请求被当匿名用户。

### 5.1 开发期 dev-login（如果你还没接通 SSO）

参考 `src/projects/starlink-factory/http.ts` 的 `/game/api/dev-login`：在中台里签发一个临时 JWT 给前端用。生产环境由你的 SSO 签发，不用这个。

```ts
// src/projects/my-business/http.ts
import { signToken } from "../../core/middleware/auth.js";
import { settings } from "../../config/settings.js";

// POST /mybiz/api/dev-login  body: {userId?}
const token = signToken({ userId: body.userId ?? "dev_user" }, settings.JWT_SECRET);
return { token, userId };
```

## 6. 平台已经替你做的事（边界）

这些**你完全不用管**，平台在 [src/server.ts](../src/server.ts) 已经做好：

- **AG-UI 协议 + SSE 流式**：模型 token 逐字推到前端，工具调用过程实时可见。
- **多步工具循环**：`stopWhen: stepCountIs(30)`，模型自主调工具直到完成任务（最多 30 步）。
- **上下文压缩**：挂载在 `createLLMClient`，每一步自动裁剪 prompt、折叠旧工具结果、滚动摘要，治 DeepSeek 长上下文幻觉。**你不需要手动精简工具返回**。
- **工具结果外置 + getArtifact**：工具完整结果存内存 artifact，context 里只留短摘要；模型需要细节时自动调 `getArtifact`（平台注入，你不用声明这个工具）。
- **线程滚动摘要**：每次对话结束自动压成摘要，下次同线程继续时注入 system prompt（跨对话的轻量记忆）。
- **对话持久化**：事件、线程、run 记录入库（MSSQL，DB-optional，挂了降级到内存不阻断）。
- **审计日志**：`[Factory]` `[tool]` `[compact]` 等标准日志（见第 12 节）。
- **CORS**：全开（`*`），前端跨域直连无障碍。
- **调试控制台**：`http://中台地址/debug` 看所有 agent / run / 事件流 / 平台决策。

## 7. 前端：对接 AG-UI 端点（Vue 3）

### 7.1 关于 copilotkit-vue 的说明

CopilotKit 官方前端 hooks（`useCoAgent` / `useCopilotAction` 等）**主要面向 React，Vue 3 支持尚不成熟**。而本中台端点是标准 AG-UI（HTTP + SSE），**任何 HTTP 客户端都能直连**——现有的 `public/game.html`、`public/inquiry.html` 都是纯 `fetch + SSE` 实现的，已在生产验证。

因此前端推荐：**Vue 3 + 原生 fetch/SSE（封装成 composable）**，不依赖 copilotkit 前端 SDK。这样最稳、最可控，且完全契合 Vue 技术栈。

### 7.2 端点清单

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/agent/{agentId}/run` | 发起一轮对话，响应体是 SSE 流 |
| POST | `/agent/{agentId}/stop/{threadId}` | 停止当前 run |

**请求头**：`Authorization: Bearer <jwt>`、`Content-Type: application/json`

**请求体**（`tools` 和 `context` 必须是数组，可空——这是 AG-UI schema 要求）：

```jsonc
{
  "threadId": "thread-abc123",           // 会话 ID，同 thread 续上下文；前端生成一个 UUID 长期复用
  "runId": "run-xyz789",                 // 本次 run 的 UUID，前端每次发消息新生成一个
  "state": {},                           // AG-UI state，业务无关传 {}
  "messages": [                          // 完整对话历史，每条含 id/role/content
    { "id": "m1", "role": "user", "content": "查一下最近的订单" }
  ],
  "tools": [],                           // 必须是数组，前端固定传 []
  "context": []                          // 必须是数组，前端固定传 []
}
```

### 7.3 SSE 事件清单

响应是 `text/event-stream`，每个事件是 `data: {JSON}\n\n`。主要事件类型：

| 事件 type | 关键字段 | 含义 |
|-----------|----------|------|
| `RUN_STARTED` | threadId, runId | run 开始 |
| `TEXT_MESSAGE_START` | message id | 一段模型文本开始 |
| `TEXT_MESSAGE_CONTENT` | `delta` | **模型吐字**，累加 delta 得到完整回复 |
| `TEXT_MESSAGE_END` | message id | 一段文本结束 |
| `TOOL_CALL_START` | toolCallId, `toolCallName` | 模型决定调某工具 |
| `TOOL_CALL_ARGS` | toolCallId, `delta` | 工具入参（流式 JSON 片段，累加） |
| `TOOL_CALL_END` | toolCallId | 入参完毕 |
| `TOOL_CALL_RESULT` | toolCallId, `content` | **工具返回**（content 是结果文本，可能是 JSON 字符串或数组） |
| `STEP_FINISHED` | stepId | 一步结束 |
| `RUN_FINISHED` | threadId, runId | run 正常结束 |
| `RUN_ERROR` | `message` / `error` | run 出错 |

最简实现只需处理 `TEXT_MESSAGE_CONTENT`（拼回复）、`TOOL_CALL_*`（展示工具调用）、`RUN_ERROR`（报错）。流自然结束即 run 完。

### 7.4 Vue 3 范例：`useAgentChat` composable

```ts
// src/composables/useAgentChat.ts
import { ref } from 'vue'

const API = import.meta.env.VITE_AGENT_API ?? 'http://localhost:9876'
const AGENT_ID = 'my_business' // ← 改成你的 agentId

function uuid() {
  return crypto.randomUUID?.() ?? Math.random().toString(36).slice(2) + Date.now().toString(36)
}

export interface ChatMessage { id: string; role: 'user' | 'assistant' | 'system'; content: string }
export interface ToolCall {
  id: string; name: string; args: string; result: string | null
  status: 'running' | 'ok' | 'reject' | 'error'
}

export function useAgentChat() {
  const messages = ref<ChatMessage[]>([])
  const toolCalls = ref<ToolCall[]>([])
  const busy = ref(false)
  let controller: AbortController | null = null

  function authHeader() {
    const t = localStorage.getItem('agent_token') ?? ''
    return { Authorization: `Bearer ${t}`, 'Content-Type': 'application/json' }
  }

  async function send(text: string) {
    const content = text.trim()
    if (!content || busy.value) return
    messages.value.push({ id: uuid(), role: 'user', content })
    busy.value = true
    controller = new AbortController()

    // threadId 跨刷新复用（同会话续上下文）
    let threadId = localStorage.getItem('agent_thread')
    if (!threadId) { threadId = uuid(); localStorage.setItem('agent_thread', threadId) }

    const body = {
      threadId,
      runId: uuid(),
      state: {},
      messages: messages.value.map(m => ({ id: m.id, role: m.role, content: m.content })),
      tools: [],
      context: [],
    }

    let buf = ''
    try {
      const resp = await fetch(`${API}/agent/${AGENT_ID}/run`, {
        method: 'POST', headers: authHeader(), body: JSON.stringify(body), signal: controller.signal,
      })
      if (!resp.ok || !resp.body) throw new Error(`run 失败 ${resp.status}`)
      toolCalls.value = []
      await consumeSSE(resp.body, (ev) => {
        const t = ev.type
        if (t === 'TEXT_MESSAGE_CONTENT') { buf += ev.delta || '' }
        else if (t === 'TOOL_CALL_START') {
          toolCalls.value.push({ id: ev.toolCallId, name: ev.toolCallName, args: '', result: null, status: 'running' })
        } else if (t === 'TOOL_CALL_ARGS') {
          const tc = toolCalls.value.find(x => x.id === ev.toolCallId); if (tc) tc.args += ev.delta || ''
        } else if (t === 'TOOL_CALL_RESULT') {
          const tc = toolCalls.value.find(x => x.id === ev.toolCallId)
          if (tc) { tc.result = textOf(ev.content); tc.status = classify(tc.result) }
        } else if (t === 'RUN_ERROR') {
          messages.value.push({ id: uuid(), role: 'system', content: '运行错误: ' + (ev.message || ev.error || '') })
        }
      })
      if (buf) messages.value.push({ id: uuid(), role: 'assistant', content: buf })
    } catch (e: any) {
      messages.value.push({
        id: uuid(), role: 'system',
        content: e.name === 'AbortError' ? '（已停止）' : '错误: ' + e.message,
      })
    } finally {
      busy.value = false
    }
  }

  async function stop() {
    const threadId = localStorage.getItem('agent_thread')
    if (threadId) {
      fetch(`${API}/agent/${AGENT_ID}/stop/${threadId}`, { method: 'POST', headers: authHeader() }).catch(() => {})
    }
    controller?.abort()
  }

  return { messages, toolCalls, busy, send, stop }
}

// ---- SSE 解析（AG-UI 流：按 \n\n 分块，取 data: 行拼 JSON）----
async function consumeSSE(body: ReadableStream<Uint8Array>, onEvent: (ev: any) => void) {
  const reader = body.getReader(); const dec = new TextDecoder(); let buf = ''
  while (true) {
    const { done, value } = await reader.read()
    if (done) break
    buf += dec.decode(value, { stream: true })
    let i
    while ((i = buf.indexOf('\n\n')) !== -1) {
      parseBlock(buf.slice(0, i), onEvent); buf = buf.slice(i + 2)
    }
  }
  if (buf.trim()) parseBlock(buf, onEvent)
}
function parseBlock(blk: string, onEvent: (ev: any) => void) {
  const dl: string[] = []
  for (const ln of blk.split('\n')) if (ln.startsWith('data:')) dl.push(ln.slice(5).replace(/^ /, ''))
  if (!dl.length) return
  const pl = dl.join('\n')
  if (pl === '[DONE]') return
  try { onEvent(JSON.parse(pl)) } catch { /* 忽略非 JSON 的心跳/注释 */ }
}
function textOf(c: any): string {
  if (c == null) return ''
  if (typeof c === 'string') return c
  if (Array.isArray(c)) return c.map((p: any) => p?.text ?? '').join('')
  try { return JSON.stringify(c) } catch { return String(c) }
}
function classify(s: string): 'ok' | 'reject' | 'error' {
  let o: any = null; try { o = JSON.parse(s) } catch {}
  if (o && typeof o === 'object') {
    if (o.ok === false && o.error === true) return 'error'
    if (o.ok === false) return 'reject'
  }
  return 'ok'
}
```

export const listOrdersTool: ToolDefinition = {

## 10. 常见坑（血泪经验）

1. **只读工具命名必须含 `view`/`list`/`detail`**。否则上下文压缩会折叠它的结果，DeepSeek 反复重查、编造数字、死循环（单轮可能调 20-50 次工具）。详见第 4.2 节。
2. **工具结果别自己精简**。直接返回完整 JSON——平台会自动外置 + 摘要。你自己截断反而可能让模型拿不到关键字段。
3. **`description` 写清楚"能做什么、返回什么、何时用"**。这是模型选工具的唯一依据。描述含糊，模型就会乱调或漏调。
4. **`tools` 和 `context` 字段必须传数组**（前端传 `[]`）。AG-UI schema 要求，不传或传 null 会 400。
5. **`JWT_SECRET` 必须和中台一致**。不一致 → 验签失败 → userId 变 `anonymous` → 你的 `resolveContext` 拿不到正确身份。
6. **写操作工具要做权限校验**（execute 内）。别只靠 prompt 约束模型——模型会违规。
7. **同 threadId 同时只能跑一个 run**。`/agent/.../run` 用同 threadId 并发会撞"Thread already running"锁。前端确保上一次回复完再发下一条（composable 里用 `busy` 互斥）。
8. **DeepSeek 偶发慢/503** 是上游端点波动（不是中台卡），重试即可。中台流式开销 < 5ms。
9. **多步任务步数上限 30**。模型陷入循环会在此被截断；若任务复杂度真需要更多步，考虑改 DAG 编排，而不是调高上限。
10. **不要在中台核心目录（`src/core/`、`src/persistence/`、`src/server.ts`）改业务逻辑**。业务全部放 `src/projects/你的项目/`，核心保持零项目耦合——这样升级中台不会冲突。

## 12. 调试

### 调试控制台

启动中台后访问 `http://中台地址/debug`：
- 看所有已注册 agent
- 看 run 列表 / 每个 run 的平台决策（路由 / 意图 / 工具子集 / 角色）
- 回放线程事件流、消息历史

### 关键日志标签（stdout）

| 标签 | 含义 |
|------|------|
| `[Factory]` | 每轮决策：agent / intent / 工具数 / 用户 |
| `[tool] {name} exec=Xms resultChars=Y summaryChars=Z stored=true` | 工具执行 + 是否外置成功 |
| `[compact] before→after (-N) Xms` | 每步上下文压缩量 |
| `[summarize]` | 线程滚动摘要 |
| `[Audit] step@+elapsedms finishReason/tools` + `run DONE in totalMs` | 每步审计 + run 总耗时 |
| `[stall]` | DeepSeek → 中台 chunk 间隔 >500ms 告警 |

排查"模型调了哪些工具、为什么乱调"时，看 `[Factory]` 和 `[tool]` 日志最快。
